#+TITLE: BabelHub
#+SUBTITLE: An Overleaf for Emacs org-mode

BabelHub renders org-mode documents in the browser and makes their source
blocks *runnable*. The wedge: do the one thing a GitHub-rendered org file
structurally cannot — execute ~#+begin_src R~ blocks — at zero marginal server
cost, by running them client-side via [[https://webr.r-wasm.org][webR]].

* Status: Tier-1 MVP

A split-pane web app:

- *Left*: a [[https://codemirror.net/][CodeMirror 6]] editor with a lightweight org-mode highlighter. Press
  *Ctrl/⌘-'* inside a source block to open it in a dedicated editor with that
  language's highlighting and completion (the browser analog of Emacs ~C-c '~) —
  Python/JS via Lezer grammars, R/bash/Julia via legacy modes; loaded lazily.
- *Right*: a live preview, parsed by [[https://github.com/rasmusbe/uniorg][uniorg]] (the same parser model as
  org-element.el — we don't roll our own).
- R and Python source blocks each get a *▶ Run* button. R runs via [[https://webr.r-wasm.org][webR]] and
  Python via [[https://pyodide.org][Pyodide]] — both client-side WASM runtimes, downloaded lazily on
  first Run (never at page load). Captured output *and plots* (R graphics,
  matplotlib figures) render inline. Each language shares one session across
  blocks, and the demo sets ~#+PROPERTY: header-args~ ~:session~ so the same
  files behave identically when opened in Emacs.

Documents *save and load* via the toolbar: each save writes the ~.org~ file to
a git-backed store on the server and commits it, so you get version history for
free. Storage lives under ~$BABELHUB_DATA~ (default ~./data~); the server needs
~git~ on the host.

Heavier code (compiled R packages, non-Python/R languages, long jobs) isn't
runnable client-side — that's the boundary with the future containerised-
execution paid tier.

The whole thing ships as a *single static Nim binary*: ~src/server~ embeds the
built frontend at compile time, so deployment is one ~scp~ — no Node, no
~dist/~ directory on the server.

* Run it

Everything is driven through *nimble* — the web build is wired in as a hook, so
you never call ~npm~ directly.

#+begin_src sh
nimble dev          # Vite dev server, hot reload  -> http://localhost:5173
nimble build        # frontend + compile the single release binary -> ./babelhub
PORT=8080 nimble run   # build + run the server     -> http://localhost:8080
nimble install      # build + install `babelhub` into ~/.nimble/bin
nimble probe        # headless check: render + Run-button wiring
nimble tidy         # remove all build artifacts (binary, dist/, nim cache)
#+end_src

(~nimble clean~ is nimble's built-in and only cleans the Nim side; ~nimble tidy~
also removes the frontend ~dist/~.)

The dev server sends ~Cross-Origin-Opener-Policy~ / ~Cross-Origin-Embedder-Policy~
headers so webR can use its fast SharedArrayBuffer channel; the production
server sets them too. Any host in front (Caddy) must pass them through.

Save/load talks to the backend at ~/api~. In dev, Vite proxies ~/api~ to
~localhost:8080~, so run the binary alongside ~nimble dev~ to exercise storage;
without it the editor still works as a scratch pad.

** Document API
- ~GET /api/docs~ → ~{"docs": [...]}~
- ~GET /api/docs/<slug>~ → the ~.org~ text (404 if absent)
- ~PUT /api/docs/<slug>~ (body = org text) → writes + commits

Slugs are ~[A-Za-z0-9_-]{1,64}~ (which also blocks path traversal).

* Container execution (Tier 3 — opt-in)

For languages webR/Pyodide can't run (bash, julia, node, …), the backend can
execute a block in an ephemeral, sandboxed container and stream back the output.
It is *off by default*; enable with ~BABELHUB_EXEC=1~:

#+begin_src sh
nimble images                                 # pre-pull the sandbox images (once)
BABELHUB_EXEC=1 PORT=8080 ./babelhub          # then blocks get a "Run (container)" button
#+end_src

Every run is locked down: ~--network none~, ~--memory~/~--cpus~/~--pids-limit~
caps, ~--read-only~ rootfs + small tmpfs, ~--cap-drop ALL~,
~--security-opt no-new-privileges~, a hard ~BABELHUB_EXEC_TIMEOUT~ (default 30s),
and a ~BABELHUB_EXEC_MAX~ concurrency cap (default 4). Code is fed on stdin.
Because the sandbox has no network, images are never pulled at run time — hence
~nimble images~.

⚠️ *Security:* this runs untrusted code. The sandbox is strong and the gate
below adds auth + rate limiting, but a public deployment should still add abuse
monitoring. The server also needs Docker-socket access for the docker runner
(run it where that's acceptable).

** Auth & rate limiting

The gate that makes server execution safe to expose:

- *Shared token* — set ~BABELHUB_TOKEN~ and every API call (documents and exec)
  needs ~Authorization: Bearer <token>~; the static app stays public and the
  ~GET /api/exec~ capability probe stays public so the page can boot. The
  frontend prompts for the token once on the first 401 and remembers it. With no
  token set, the API is open (local/dev). This is a single shared secret —
  per-user identity (GitHub OAuth) is the next step.
- *Rate limit* — exec is capped at ~BABELHUB_RATE~ requests per
  ~BABELHUB_RATE_WINDOW~ seconds, per client IP (X-Forwarded-For aware, for
  behind Caddy); over the limit returns ~429~ with ~Retry-After~.

** GitHub OAuth (per-user identity)

Beyond the shared token, BabelHub can authenticate *individual* users via
GitHub. Register an OAuth App (callback URL ~<base>/auth/callback~) and set:

#+begin_src sh
BABELHUB_GH_CLIENT_ID=...  BABELHUB_GH_CLIENT_SECRET=...  \
  BABELHUB_BASE_URL=https://babelhub.example.com  BABELHUB_EXEC=1 ./babelhub
#+end_src

The flow is the standard authorization-code dance with a CSRF ~state~:
~/auth/login~ → GitHub → ~/auth/callback~ sets an httpOnly session cookie;
~/auth/logout~ ends it; ~GET /api/me~ returns the login. The toolbar shows a
*Login with GitHub* button (then ~@you~ / logout).

Each logged-in user gets a *private document namespace* — their docs live in a
per-user git repo under ~$BABELHUB_DATA/<login>/~, separate from everyone else's
(anonymous use falls back to the shared store). Sessions are in-memory, so a
restart logs everyone out. With OAuth on, the API requires a session (the shared
token still works too, if also set).

#+begin_src sh
BABELHUB_EXEC=1 BABELHUB_TOKEN=$(openssl rand -hex 16) \
  BABELHUB_RATE=30 PORT=8080 ./babelhub
#+end_src

API: ~GET /api/exec~ → ~{"enabled","languages","sessionLanguages"}~;
~POST /api/exec~ with ~{"lang","code"}~ → ~{"ok","output"}~ (403 when disabled).

** Persistent sessions (R / Python)

R and Python run client-side by default (webR/Pyodide). When ~BABELHUB_EXEC=1~,
the toolbar shows a *Run: browser ⟷ session* toggle; in *session* mode those
blocks run server-side in a *persistent* container instead — one long-lived
interpreter per (document, language), so state is shared across blocks like a
Jupyter kernel and like org-babel's ~:session~. A fitted model in one block is
available in the next; an error doesn't kill the session.

Session results are rich, not just text: *plots* are captured (R graphics
devices, matplotlib figures) and rendered inline, and a *tabular* last value (an
R ~data.frame~/matrix or a pandas ~DataFrame~) is returned as a structured table
and rendered as HTML (capped at 200 rows).

Under the hood each interpreter runs a small driver speaking a length-framed
protocol over stdin/stdout; the reply is JSON ~{output, images, tables}~.
~POST /api/exec~ with an extra ~"session"~ field routes to the session for that
document. Idle sessions are reaped.

Runner (~BABELHUB_EXEC_RUNNER~):
- ~docker~ (default) — the interpreter runs in the same locked-down sandbox as
  above (plus a writable ~/tmp~ + ~/home~ tmpfs). Needs ~python:3.12-slim~ and
  ~r-base~ images (~nimble images~ pulls them).
- ~local~ — the interpreter runs directly on the host (no isolation). Fine for a
  single trusted user; this is what the driver tests exercise.

Config knobs: ~BABELHUB_EXEC~, ~BABELHUB_EXEC_RUNNER~, ~BABELHUB_EXEC_TIMEOUT~,
~BABELHUB_EXEC_MEM~, ~BABELHUB_EXEC_CPUS~, ~BABELHUB_EXEC_MAX~ (ephemeral
concurrency), ~BABELHUB_SESSION_MAX~ (live sessions), ~BABELHUB_SESSION_IDLE~
(idle reap, seconds), ~BABELHUB_TOKEN~ (shared auth token),
~BABELHUB_RATE~ / ~BABELHUB_RATE_WINDOW~ (exec rate limit).

* Ship it (single binary)

~nimble build~ produces ~./babelhub~ — the frontend is embedded, so that one
file is the whole deploy. To a Hetzner box: ~scp babelhub root@host:/usr/local/bin/~,
drop in ~server/deploy/babelhub.service~ (systemd) and ~server/deploy/Caddyfile~
(TLS + reverse proxy), then ~systemctl enable --now babelhub~.

* Run it in a container

The self-contained binary makes this trivial — the image is just a base + the
binary, no Node, no ~dist/~.

#+begin_src sh
nimble drun        # build image + (re)launch on :8080 with a data volume
#+end_src

~nimble drun~ is the one-step recipe: it builds the image, removes any previous
~babelhub~ container, and starts a fresh one. The expanded form it runs:

#+begin_src sh
docker build -t babelhub .
docker rm -f babelhub 2>/dev/null || true   # `docker run` never replaces a container
docker run -d --name babelhub -p 8080:8080 -v babelhub-data:/data babelhub
#+end_src

Two things worth knowing:

- *~docker run~ is not idempotent* — each call creates a new container, so a
  second ~docker run -p 8080:8080~ fails with "port is already allocated" until
  you ~docker rm -f babelhub~. Naming the container (as above) makes replacing
  it a one-liner.
- *Persist documents.* Saved docs live at ~/data~ inside the container and die
  with ~docker rm~. The ~-v babelhub-data:/data~ named volume keeps them across
  restarts.

The ~Dockerfile~ builds everything itself (frontend, then the embedding Nim
compile) so it needs no host toolchain. For an even smaller =scratch= image,
~nimble staticbin~ builds a fully-static musl binary.

Note: this containerises *BabelHub itself*. Running each org *code block* in its
own container is the separate Tier-3 execution backend — today's R blocks run
client-side in webR (no container), and this design leaves room to add the
container-per-block backend later without rework.

* Layout

| Path                | Role                                            |
|---------------------+-------------------------------------------------|
| ~src/render.ts~     | org text → HTML via the uniorg/unified pipeline |
| ~src/run.ts~        | lazy webR boot + Run-button wiring              |
| ~src/main.ts~       | editor ↔ debounced render ↔ buttons             |
| ~src/editor.ts~     | CodeMirror + org StreamLanguage highlighter     |
| ~src/srcedit.ts~    | dedicated per-language block editor (Ctrl-')    |
| ~src/storage.ts~    | client for the /api document store              |
| ~public/sample.org~ | demo document loaded on first paint             |
| ~scripts/probe.ts~  | jsdom verification of the render+run wiring      |
| ~server/babelhub.nim~ | Nim server; embeds dist/ → single binary      |
| ~server/storage.nim~ | git-backed document store + API                |
| ~server/exec.nim~   | ephemeral sandboxed execution (Tier 3, opt-in)  |
| ~server/session.nim~ | persistent session interpreters (R/Python)     |
| ~server/gate.nim~   | shared-token auth + per-IP rate limiter         |
| ~server/oauth.nim~  | GitHub OAuth login + sessions                   |
| ~src/api.ts~        | token/OAuth-aware fetch, /api/me                 |
| ~babelhub.nimble~   | one entry point: build/run/install/docker tasks |
| ~Dockerfile~        | self-contained image build                      |
| ~server/deploy/~    | systemd unit + Caddyfile for the Hetzner box    |

* Roadmap

Sequenced cheapest-first, each step independently shippable.

** Tier 1 — free, near-zero server cost (this MVP)
- [X] uniorg render + webR Run buttons
- [X] CodeMirror editor surface with org highlighting
- [X] Capture and inline plots (webR graphics device → canvas)
- [X] Single static Nim binary serving the embedded site
- [X] Save/load documents via git-backed storage
- [X] Python execution via Pyodide (stdout + matplotlib figures)
- [ ] Org-aware diff view (heading/subtree level, not line-based)

** Tier 2 — still serverless-ish
- [ ] Export-as-a-service via GitHub Actions (PDF/Beamer/HTML; GitHub's compute)
- [ ] Org-aware diff bot posting PR comments

** Tier 3 — paid, real backend (Nim)
- [ ] Single static Nim binary (Jester/Prologue) on Hetzner CX23 + Caddy TLS
- [ ] GitHub OAuth, Stripe billing, Git-backed storage + Postgres metadata
- [ ] Containerised, scale-to-zero execution for heavy/compiled workloads
      (fastsem, Nim, R packages webR can't reach), billed per-second

** Endgame
- [ ] BYOC orchestration: run blocks in the customer's *own* cloud account
- [ ] Compliant workbench plugging into All of Us / ABCD enclaves
